# 知识库迭代机制 2.0：LLM 编译版

> [!info] 这份方案解决什么问题
> 不是单纯把资料收进 Obsidian，而是把 `Clippings + Horizon + Obsidian + LLM` 变成一个会持续“编译、回答、回写、巡检”的知识系统。

## 一、这次升级的依据

这份机制基于 Andrej Karpathy 在 `https://x.com/karpathy/status/2039805659525644595` 的原文思路整理而成。  
你已经提供了帖子的完整正文，因此这里直接按原文结构吸收，而不再依赖转述。

Karpathy 的关键思路不是“写更多笔记”，而是把知识库当成一套可被 LLM 持续维护的编译系统：

1. 把原始资料统一放进 `raw 原始资料/` 一类的原始层。
2. 让 LLM 增量“编译”出 wiki，而不是每次问问题都回到原始资料现查。
3. wiki 本身是由 `.md` 文件、摘要、索引、反向链接、概念页构成的结构化知识层。
4. Obsidian 主要承担前端 IDE 角色，用来看原始资料、编译结果和派生输出。
5. 问答最好输出为 Markdown、幻灯片、图表等文件，而不是一次性聊天文本。
6. 输出结果经常继续归档回 wiki，让每次探索都能积累进知识库。
7. 要定期对 wiki 做 health checks，查不一致、缺失项、潜在新连接和新条目候选。
8. 当知识库增长后，可以继续加搜索工具、CLI 工具，甚至探索合成数据与微调。

对你来说，最重要的不是照搬他的目录结构，而是把你现有的：

- `raw 原始资料/clippings 网页剪藏/`
- `AI信息收集系统/`
- `Projects/Horizon/`
- Obsidian Web Clipper
- Horizon 日报

接成一个真正闭环。

## 二、你当前知识库的现状判断

### 已经有的优势

1. 你已经有 `raw 原始资料/clippings 网页剪藏/`，说明原始资料采集入口存在。
2. 你已经有 `Projects/Horizon/` 和日报入口，说明外部信息流可以持续进入库内。
3. 你已经把信息收集系统单独放到 `AI信息收集系统/`，天然适合做控制台。
4. 你已经启用了 Web Clipper，说明网页转 Markdown 的成本已经很低。

### 当前主要缺口

1. 现在更像“资料仓 + 日报入口”，还不是“知识编译系统”。
2. Horizon 日报进入库后，缺少明确的二次提炼动作。
3. 缺少“主题页 / 索引页 / 观点页 / 决策页”的分层。
4. 缺少“问答结果回写”的机制，查询结束后没有稳定沉淀。
5. 缺少固定频率的库内巡检机制。

一句话判断：**你现在有采集入口和日报雷达，但还没形成 Karpathy 所说的“LLM 持续编译并维护 wiki”的机制。**

## 三、新机制的总原则

> [!summary] 2.0 总原则
> 原始材料不直接等于知识。  
> `raw 原始资料/clippings 网页剪藏/Horizon` 负责供给原始材料，LLM 负责把材料增量编译成 wiki，Obsidian 负责作为前端 IDE 来查看、提问、产出和回写。

以后你的知识库按六层运转：

1. **原始层**：收材料，不急着改写。
2. **编译层**：把材料增量编译成 wiki。
3. **索引层**：维护主题索引、摘要页、反向链接、概念关系。
4. **问答层**：围绕真实问题生成答案、比较、方案、图表。
5. **回写层**：把输出结果再归档回 wiki。
6. **巡检层**：定期做 health check，修补和扩展知识库。

## 四、你的定制版结构

在不大改现有目录的前提下，建议这样定义每个区域的职责：

### 1. `raw 原始资料/clippings 网页剪藏/` = 原始资料池

只放原文，不追求漂亮。

适合放：

- 网页剪藏
- 长文、教程、博客、访谈
- 临时保存的资料原文

要求：

- 不在这里做深度改写
- 文件名尽量保留原题目
- 每篇只负责“存档 + 可回溯”

### 2. `Projects/Horizon/data/summaries/` = 外部信号流

这里不是知识结论，而是“今天外界值得看什么”。

用途：

- 每日发现候选主题
- 追踪 AI、工具、论文、产品变化
- 给每周知识编译提供素材入口

规则：

- Horizon 日报不直接当成知识结论
- 只把其中值得长期沉淀的内容送入编译层
- 如果某个主题连续多天出现，就提升其编译优先级

### 3. `AI信息收集系统/` = 知识编译控制台

这个目录以后不只放 Horizon 配置，而是作为你的知识系统驾驶舱。

建议在这里长期维护 4 类文档：

- `入口页`：系统总览、最近更新、优先事项
- `机制页`：这份迭代方案
- `主题索引页`：你当前正在持续积累的主题与概念入口
- `回顾页`：每周 / 每月知识复盘

### 4. 主题知识页 = 编译后的 wiki 资产层

建议后续逐步增加一个主题层，用于承接被编译后的知识。名称你可以保持直白，例如：

- `AI信息收集系统/主题 - Agents.md`
- `AI信息收集系统/主题 - RAG.md`
- `AI信息收集系统/主题 - Obsidian工作流.md`

每个主题页只做 6 件事：

1. 定义主题是什么
2. 汇总核心概念
3. 维护相关资料摘要
4. 链接原始资料
5. 记录你的判断
6. 指向未解决问题

## 五、新的迭代闭环

## 阶段 1：原始资料采集

入口只有两个：

1. `raw 原始资料/clippings 网页剪藏/` 收长内容原文
2. `Horizon` 收持续外部动态

规则：

- 看见有价值的网页，先剪藏，不急着总结
- 相关图片尽量本地化，避免后续 LLM 只能看到失效外链
- Horizon 里出现连续 2 到 3 次的主题，标记为“值得编译”

## 阶段 2：增量编译 wiki

每周只做少量高价值编译，不追求全量处理。

编译动作：

1. 从本周 Horizon 和 Clippings 中选 **1 到 3 个主题**
2. 让 LLM 基于这些原始材料更新已有主题页，或新建主题页
3. 输出该主题的：
   - 核心定义
   - 关键分支
   - 代表人物 / 工具 / 论文 / 案例
   - 与你已有兴趣的关系
   - 下一步值得追踪的问题
4. 同步补索引、摘要、链接关系

编译产物不是“读后感”，而是：

- 主题综述
- 术语表
- 时间线
- 对比表
- 资源索引
- 文档摘要页
- 主题入口页

## 阶段 3：围绕 wiki 问答

当你有真实问题时，不再直接对着一堆原文问。

正确做法：

1. 先让 LLM 查看相关主题页
2. 再让它回看相关摘要页和原始资料
3. 必要时补充外部检索
4. 输出单独答案文件，而不是只在聊天里看结果

适合沉淀的问答产物：

- “我该先学什么”
- “A 和 B 的关键差异”
- “这项技术对我当前项目有什么用”
- “最近两周这个方向发生了什么变化”

## 阶段 4：输出文件化

Karpathy 原文里有一个很关键的点：  
**不要只拿终端文本答案，而要让 LLM 产出文件。**

所以你的系统里，优先产出：

- Markdown 分析页
- 幻灯片草稿
- 对比表
- 简单图表
- 研究问题清单

这些都应该能在 Obsidian 里直接查看。

## 阶段 5：回写归档

这是你当前最缺的一步，也是 Karpathy 思路里最值钱的一步。

所有高质量输出都尽量回写成库内对象：

- 好的回答，回写成主题页中的一个章节
- 好的比较，回写成独立对比页
- 好的行动建议，回写成项目决策页
- 好的问题清单，回写成待研究列表

判断是否回写，只看一个标准：

> 这个结果未来 30 天内我还会不会再次用到？

如果会，就不要让它停留在聊天记录里。

## 阶段 6：健康检查与巡检

每周做一次轻巡检，每月做一次深巡检。

### 每周巡检

检查：

1. 本周新资料里，有哪些重复出现的主题？
2. 哪些主题页超过 14 天没更新但外部变化很快？
3. 哪些主题页只有资料链接，没有你的判断？
4. 哪些问答结果还没回写？
5. 哪些摘要页、索引页还不够用？

### 每月巡检

检查：

1. 哪些主题已经足够成熟，可以收敛成一篇总览？
2. 哪些主题实际上已经不再重要，应降级处理？
3. 哪些概念命名不一致，需要统一？
4. 哪些资料只有摘要没有原文来源，需要补链？
5. 哪些领域值得新增 Horizon 信息源？
6. 哪些主题已经值得单独做搜索工具或命令行工具？

## 六、你现在最适合执行的节奏

### 每天 15 分钟

1. 看 Horizon 日报
2. 标记 1 到 3 个值得进一步研究的点
3. 把临时看到的长文丢进 `raw 原始资料/clippings 网页剪藏/`

### 每周 60 到 90 分钟

1. 从本周材料里选一个主题
2. 让 LLM 生成或更新主题页、索引页、摘要页
3. 产出一篇“本周我真正学到了什么”
4. 把高质量输出回写

### 每月 90 分钟

1. 做一次知识库健康检查
2. 合并重复主题
3. 补齐关键索引页
4. 调整 Horizon 信息源

## 七、建议你统一的笔记对象类型

为了避免以后越积越乱，建议把知识对象分成 5 类：

### 1. 原始资料

放在 `raw 原始资料/clippings 网页剪藏/`

特点：

- 原文为主
- 少改写
- 可追溯

### 2. 主题页

用来沉淀长期认知。

特点：

- 会持续更新
- 是问答的主入口
- 会链接多个原始资料

### 3. 问题页

围绕一个真实问题展开。

例如：

- `问题 - RAG 现在还有必要学多深吗？`
- `问题 - Obsidian + LLM 的最佳组合是什么？`

### 4. 输出页

面向使用场景的结果页。

例如：

- 调研报告
- 学习路径
- 方案比较
- 演讲提纲

### 5. 回顾页

记录本周 / 本月系统层面的认知变化。

这类页最重要，因为它会告诉你：

- 你最近真正关心什么
- 你的知识结构正在往哪里偏
- 哪些输入源在浪费你的注意力

### 6. 索引页 / 摘要页

这是 Karpathy 方案里非常关键但最容易被忽略的对象。

用途：

- 帮 LLM 缩短查找路径
- 降低每次问答读取原文的成本
- 让“无需复杂 RAG 也能工作”成为可能

## 八、给你的一套执行判断标准

以后每条信息都只问 4 个问题：

1. 这是 **短期资讯**，还是 **长期主题素材**？
2. 它应该停在 `raw 原始资料/clippings 网页剪藏/Horizon`，还是要进入主题页？
3. 它是补充事实，还是改变了我的判断？
4. 它能不能被回写成以后可复用的资产？

如果只是“知道了”，不必进主题页。  
如果它改变了你的理解、路径或选择，就应该进入编译层。

## 九、建议你马上开始的最小动作

不要一次性大改库结构，先做下面 4 件事：

1. 以后把所有网页材料继续收进 `raw 原始资料/clippings 网页剪藏/`
2. 每周从 Horizon 日报里只选 1 个主题做编译
3. 每次重要问答都落成单独 Markdown 文件
4. 每周把最有价值的问答回写到主题页

## 十、这个机制升级后，你的知识库会发生什么变化

升级前：

- 资料越来越多
- 入口越来越多
- 真正可复用的判断不够多

升级后：

- 原始资料持续增加，但不会直接污染主知识层
- 主题页会越来越稳，成为你的长期认知骨架
- 问答不再是一次性消费，而会反过来增强知识库
- Horizon 不再只是“日报工具”，而是你的外部雷达
- Obsidian 不再只是“笔记软件”，而是你的知识 IDE 前端
- LLM 不再只是回答问题，而是开始维护你的 wiki

## 十一、从原文补出的两个关键提醒

> [!warning]
> 这套机制不是“全文自动丢进去就万事大吉”。
> 真正的关键是：LLM 要持续维护摘要、索引、概念页和链接关系，否则后面的问答质量会明显下降。

> [!warning]
> 原文里对 Output 的意思是“我喜欢让它渲染成 markdown、slides、matplotlib 图，再回到 Obsidian 里看”，不是“我不喜欢”。
> 所以你的机制里，文件化输出必须是默认动作，而不是可选动作。
