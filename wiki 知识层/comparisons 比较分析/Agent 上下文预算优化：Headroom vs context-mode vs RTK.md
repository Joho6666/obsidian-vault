# Agent 上下文预算优化：Headroom vs context-mode vs RTK

## 这页比较什么

- 这三个项目都在解决同一个问题：工具输出太长、太噪、太贵，不能直接原样塞给 LLM。
- 但它们切入的位置不同，所以适合的工作流也不同。

## 快速结论

- `Headroom`：适合需要保留原文可回溯性的压缩场景，尤其是日志、文件和 RAG 块。
- `context-mode`：适合编码代理场景里先按任务意图过滤，只把相关片段交给模型。
- `RTK`：适合不想重写现有工作流，只想在命令输出层立即减少 token 开销的 CLI 代理路线。

## 对比表

| 项目 | 主要形态 | 核心机制 | 更适合的场景 | 局限 |
|---|---|---|---|---|
| Headroom | 库 + Agent + MCP server | 可逆压缩，必要时再取原文 | 日志、文件、RAG 块、多源工具输出 | 仍需设计恢复原文的调用链 |
| context-mode | MCP server / 上下文优化层 | 先索引再检索，按任务意图筛片段 | 编码代理、长工具输出、跨文件定位 | 更依赖任务描述质量与检索命中 |
| RTK | CLI proxy | 对常见开发命令做透明压缩 | `git diff`、测试输出、容器日志、现成 CLI 工作流 | 覆盖面受支持命令与 hook 接入限制 |

## 差异判断

### 1. 它们插入工作流的位置不同

- `Headroom` 更像“压缩组件”，可以嵌到多类系统里。
- `context-mode` 更像“上下文入口守门员”，决定哪些信息可以进模型。
- `RTK` 更像“命令输出代理”，尽量不改工作流，只改输出进入模型前的那一层。

### 2. 它们优化的对象粒度不同

- `Headroom` 面向日志、文件、RAG 块这类通用文本对象。
- `context-mode` 面向“当前任务真正需要哪些上下文片段”。
- `RTK` 面向 shell / CLI 命令输出这种开发者高频噪声源。

### 3. 它们对应的工程目标不同

- 如果你最关心“保留信息完整性”，优先看 `Headroom`。
- 如果你最关心“减少无关上下文”，优先看 `context-mode`。
- 如果你最关心“立刻把成本打下来”，优先看 `RTK`。

## 当前判断

- `Headroom` 最像可复用基础组件。
- `context-mode` 最像编码代理专用的上下文选择层。
- `RTK` 最像低摩擦、可快速验证 ROI 的接入方案。
